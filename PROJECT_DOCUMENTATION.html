Overview — what this is & why

A documentation-first project. There is no application to run — the deliverable is a written guide, wrapped in a working dual-agent harness that demonstrates the very features it documents.

This repository has two faces. The visible deliverable is coding-agents-practice-guide.md — a ~1,200-line comparative reference that documents every feature surface of Claude Code (Anthropic) and OpenAI Codex CLI side by side: architecture, installation, CLI commands and flags, the TUI, slash commands, permission/approval modes, instruction files, skills, hooks, plugins, MCP, subagents and agent teams, headless mode, sandboxing, configuration files, IDE integration, CI/CD, cloud surfaces, scheduling, models, context management, checkpointing, the agent SDK, channels, enterprise governance, applied exercises, and a feature cross-reference matrix.

The second face is the repository itself: a fully wired, OS-agnostic harness that lets both agents edit this repo with the same behavior. It carries parallel instruction files (CLAUDE.md for Claude Code, AGENTS.md for Codex), a shared set of Node-based lifecycle hooks under scripts/hooks/, a Codex hook registration in .codex/hooks.json, slash commands in .codex/commands/, and a phase-awareness skill in .agents/skills/. The harness is itself a worked example of sections 7–9 of the guide.

Audience & intent. The reader is a senior engineer who already uses coding agents daily and wants deep, comparative mastery — not a beginner tutorial. The project's prime directive (from CLAUDE.md §0) is accuracy over coverage: every feature claim must be verifiable against official docs or observed CLI behavior, and comparative tables must be fair to both platforms with no editorializing about which is "better."

Key concept
This is a reference/practice project, not a software application. There is no FastAPI service, no React frontend, no database, no Docker. The "code" here is the harness (hooks + config + CI), and the "product" is prose. Phase 2 (interactive exercises) and Phase 3 (benchmarking tools) are planned but not built.

Current state. Phase 1 — Curated Reference Documentation — is active and the guide exists as a complete first draft (all 27 sections, with Mermaid diagrams, comparative tables, and exercises). Version is v0.1.0. The remaining Phase 1 work is an accuracy audit against official docs and closing the phase-completion gate (see Roadmap).

Watch out — documentation drift
Several docs were written before the harness was added and are now stale. README.md and the file-inventory blocks in CLAUDE.md / AGENTS.md describe a .claude/ directory with settings.json, commands/, and skills/. That directory does not exist in the repo (it is gitignored). The real harness lives in scripts/hooks/, .codex/, and .agents/. They also state "no pyproject.toml," but pyproject.toml now exists as the version source of truth for CI. These mismatches are flagged throughout this page.

Tech stack

This is a documentation project, so the "stack" is deliberately thin: Markdown for content, Node for hooks, Python's packaging metadata for versioning, and GitHub Actions for release automation.

Architecture

Two layers: a content layer (the guide and supporting docs) and a harness layer (instruction files, hooks, commands, skills, CI) that governs how agents edit the content.

Dual-agent symmetry

The defining architectural choice is agent symmetry: every harness piece exists in a form both Claude Code and Codex understand, so the repo behaves identically no matter which agent opens it.

ConcernClaude Code readsCodex readsShared implementation
Instruction fileCLAUDE.mdAGENTS.mdByte-identical content, agent name swapped
Lifecycle hooks(its own settings).codex/hooks.jsonSame .cjs files in scripts/hooks/
Slash commands(its own dir).codex/commands/review.md, pre-commit.md
Skills(its own dir).agents/skills/phase-awareness/SKILL.md
Key concept — one hook codebase, two agents
The hooks read tool data from stdin as JSON (not from environment variables), and resolve the project root from CLAUDE_PROJECT_DIR with a process.cwd() fallback. That single design lets the exact same .cjs file run under both agents. See scripts/hooks/hookUtils.cjs.

The dual-agent harness (hooks, commands, skills)

The harness is the only "code" in the repo. It is a worked, self-referential example of the guide's sections 7–9 — and it enforces the project's content and git rules automatically.

Shared hook utilities scripts/hooks/hookUtils.cjs

The foundation every hook imports. It resolves the project root, reads the JSON payload off stdin, classifies sensitive paths, and provides read-only git helpers. Note the OS-agnostic design: it never relies on $CLAUDE_FILE_PATH or shell tooling — tool data arrives as stdin JSON.

The sensitive-path guard (isSensitivePath) blocks .env / .env.* (except .example/.sample/.template), anything named credentials.* or secrets.*, and key material (.pem, .key, .p12, .pfx, id_rsa, id_ed25519, .tokens/). The gitOutput helper runs git read-only with an injected safe.directory so it works on Windows-mounted paths.

scripts/hooks/hookUtils.cjs171 lines. Its module.exports block exports 13 names — 12 helper functions plus the PROJECT_DIR constant — consumed by the four hook entrypoints.
PreToolUse — sensitive-write guard scripts/hooks/pre-tool-use.cjs

Reads the payload, extracts the target file, and if it matches isSensitivePath emits a block decision. Otherwise it is a no-op.

Registered against the Write|Edit matcher (.codex/hooks.json) with a 3s timeout. Any error is swallowed (process.exitCode = 0) so a hook bug never blocks legitimate edits.

PostToolUse — content-rule injection scripts/hooks/post-tool-use.cjs

After any edit, it matches the edited path against a small rule set and injects contextual guidance via hookSpecificOutput.additionalContext. Editing the guide re-states the content rules (verifiability, fairness, no stubs, diagrams); editing AGENTS.md or the master plan re-states the docs-consistency and phase constraints.

Stop hooks — git nudge + memory review scripts/hooks/stop.cjs · stop-memory.cjs

stop.cjs lists uncommitted files via read-only git and emits a systemMessage reminding that the user manages git (so the agent must only suggest a commit message) and that docs/ may need updating if source changed without it. stop-memory.cjs emits a separate prompt nudging a memory review at session end — which memory type to use and what is/ isn't worth saving.

scripts/hooks/stop.cjsUncommitted-files + docs-drift nudge.
scripts/hooks/stop-memory.cjsSession-end memory-review prompt.
Do not
No hook here ever runs a mutating git command. The stop hook deliberately only reports uncommitted state and suggests a message. The user manages git exclusively (CLAUDE.md §5).
Codex commands — /review and /pre-commit .codex/commands/

/review runs a four-part content audit (accuracy, fairness, completeness, style) over changed files and produces a severity-tagged checklist with a READY / NOT READY verdict — and never auto-fixes. /pre-commit wraps /review plus documentation-state, internal-consistency, Mermaid, and phase-alignment checks into a single verdict table; it is strictly read-only and never stages or commits.

.codex/commands/review.mdContent accuracy review protocol.
.codex/commands/pre-commit.mdRead-only pre-commit audit.
phase-awareness skill .agents/skills/phase-awareness/SKILL.md

Applied at session start and before any content work. It states exactly what Phase 1 IS (writing/refining the guide, diagrams, tables, exercises, docs) and what it is NOT (no Python, notebooks, Streamlit, Docker, launchers, benchmarks). If a request crosses a phase boundary, the skill instructs the agent to name the target phase, refuse to implement it, and suggest noting it in the master plan.

Content rules & quality gates

Because the product is prose, "correctness" is defined by content rules rather than passing tests. These are the load-bearing constraints every contribution must satisfy.

Accuracy
Every feature claim must be verifiable against official docs or observed --help output. Uncertain claims are marked (unverified) or (as of [date]). CLI syntax must be copied/tested, never invented. Version-introduced features note their version.
Fairness
Comparative tables present each agent's actual capabilities — no strawmanning. Feature gaps are stated factually with zero editorial "better/worse" commentary.
Completeness
Each section should carry concept + both agents' implementations + a comparative table + at least one exercise. No "TBD"/"coming soon" stubs — write it or omit the header.
Style
Technical, terse, high-signal. Code blocks carry the right language id. Tables (not prose) for comparisons. Blockquotes for warnings.

The four content quality gates

GateMeaningEnforced by
VerifiabilityEvery claim traceable to official docs / --help./review accuracy audit
FairnessTables show real capabilities, no bias./review fairness audit
CompletenessNo stubs, no empty table rows./review completeness audit · phase gate
DiagramsMermaid for every architecture/flow concept./pre-commit Mermaid check
Tip
The PostToolUse hook re-injects the content rules every time you touch the guide, so you do not have to remember them — but the authoritative statement lives in docs/CODING_AGENTS_TOOLING_MASTER_PLAN.md §4 and CLAUDE.md §3.

Versioning & release

Strict semver, applied to content. There are two coupled sources: the human changelog and the machine-readable version field.

BumpTriggers
patchCorrections / clarifications to existing content.
minorNew sections or newly-covered features.
majorRestructuring the guide or adding a third agent.
  • Human changelog: docs/versions.md — newest entry on top; currently a single v0.1.0.
  • Machine version: the version field in pyproject.toml, bumped only by CI.
  • Release: trigger the GitHub Action with a bump input — it runs uv version --bump, commits, tags vX.Y.Z, and pushes.
Watch out — agent must not bump the version
The release workflow is the only thing that edits pyproject.toml's version and creates tags. An agent should update docs/versions.md with the computed next version as a documentation entry, but never touch the version field or run git. (Per the global versioning + git policies.)

How to read / use it

There is nothing to "run" — the deliverable is read, and the harness activates automatically when an agent opens the repo.

Read the guide

  1. Open coding-agents-practice-guide.md in any Markdown viewer with Mermaid support (GitHub, GitLab, VS Code + Mermaid extension).
  2. Jump via the in-file table of contents to the feature you need.
  3. Work the exercises in §26; use the §27 matrix to check feature availability across agents.

Launch an agent on this repo

  1. Open the repo with Claude Code (claude) or Codex (codex). The instruction file and hooks load automatically.
  2. To enable Claude Code agent-teams, launch via claude-teams.sh (macOS/Linux) or claude-teams.bat (Windows) — both export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 and exec the CLI.
  3. Run /review before suggesting a commit; run /pre-commit for the full audit verdict.
Note — hooks need Node
The lifecycle hooks shell out to node. Node must be on PATH for the harness to function under either agent. No other runtime is required for Phase 1.
Watch out — no launcher loop
There is intentionally no run_*.sh/run_*.bat with the [k]/[q]/[v]/[r] Docker shutdown loop the user's other projects use — that pattern is for containerized apps and is explicitly deferred until Phase 2 (CLAUDE.md §2). claude-teams.* are plain exec wrappers, not the launcher contract.

How to edit / extend it

Practical, owner-focused recipes. For each common change, this is exactly which files to touch and which rules to respect.

Add or revise a guide section
  1. Edit coding-agents-practice-guide.md. Add the numbered heading, update the in-file Table of Contents at the top, and keep section numbering contiguous.
  2. Satisfy the section shape: concept → both agents' implementations → a comparative table → (where it clarifies) a Mermaid diagram → an exercise. The PostToolUse hook will remind you.
  3. Verify every claim against official docs; mark uncertain ones (unverified)/(as of [date]).
  4. Bump docs/versions.md (minor for a new section) and refresh docs/status.md.
  5. Run /review, then /pre-commit. Suggest a commit message — do not commit.
Add a new lifecycle hook
  1. Create scripts/hooks/<name>.cjs importing helpers from scripts/hooks/hookUtils.cjs. Read the payload with readHookPayload(); emit with emit().
  2. Register it in .codex/hooks.json under the correct event, using the node -e require(...) pattern and a timeout.
  3. Keep it OS-agnostic: read tool data from stdin JSON, never from env vars; swallow errors with process.exitCode = 0 so a bug can't block edits.
Do not
Do not write hooks in bash/jq/python. The global rule (and this repo's existing hooks) require Node .cjs so they run on Windows cmd.exe and macOS alike. Do not have a hook run a mutating git command.
Add a Codex slash command
  1. Create .codex/commands/<name>.md with YAML frontmatter (name, description) and a body of step-by-step instructions.
  2. Start the body with "Before anything else: re-read AGENTS.md, read the master plan, read docs/status.md" — mirroring the existing review.md / pre-commit.md.
  3. If it audits, it must be read-only and never stage/commit.
Add a skill
  1. Create .agents/skills/<name>/SKILL.md with frontmatter (name, description that states the trigger condition) and a protocol body — follow phase-awareness/SKILL.md as the template.
  2. Skills enforce invariants proactively; keep them focused on one concern.
Cut a release
  1. On main, trigger the Release workflow (.github/workflows/release.yml) with bump = patch|minor|major.
  2. CI bumps pyproject.toml, commits release: vX.Y.Z, tags, and pushes. Do this yourself — agents do not run it.
Tip — fix the documentation drift first
If you do one cleanup, reconcile the stale inventories: update the trees in README.md, CLAUDE.md, and AGENTS.md to reflect the real scripts/hooks/, .codex/, .agents/, .github/, pyproject.toml, and launcher files. That single edit removes the biggest source of confusion for a new contributor.

Testing & validation

Phase 1 has no executable product, so "testing" means content validation, not unit tests.

  • Run /review to audit accuracy, fairness, completeness, and style on changed files (.codex/commands/review.md).
  • Verify every Mermaid diagram renders (Mermaid live editor or a Markdown preview).
  • Verify in-file section anchors resolve.
  • Verify every comparative-table row has entries for both agents.
Note — no test runner, by design
There is no pytest/Vitest, no coverage gate, and no test directory in Phase 1 — correct for a documentation project. Test harnesses arrive only with Phase 2/3 executable code. The user's global 100%-coverage rule applies to code, of which there is none here beyond the small hooks.

Domain glossary

Terms a newcomer needs to read the guide and the harness fluently.

Claude Code
Anthropic's terminal-first coding agent (TypeScript/Node). Reads CLAUDE.md, configured via JSON settings.json.
Codex CLI
OpenAI's coding agent (Rust). Reads AGENTS.md, configured via TOML config.toml; sandboxes at the OS level.
Instruction file
The Markdown contract an agent reads before working (CLAUDE.md / AGENTS.md). Defines rules, scope, and conventions.
Hook
A user script invoked at a lifecycle event (PreToolUse, PostToolUse, Stop, …) that can block, inject context, or report.
Skill
A reusable instruction bundle (SKILL.md + optional scripts/refs) the agent loads on demand or by user command.
Slash command
A user- or built-in command invoked as /name that runs a defined protocol (e.g. /review).
MCP
Model Context Protocol — a standard for connecting agents to external tools/data over stdio or HTTP; tools are named mcp__<server>__<tool>.
Subagent / Agent team
A spawned helper agent (e.g. security review) reporting back to a lead; Claude can isolate each in a git worktree.
Permission / approval mode
How much autonomy the agent has — Plan/Auto/Bypass (Claude) vs. Read-Only/Auto/Full-Access (Codex).
Sandbox
The mechanism constraining what the agent can touch — app-level classifier (Claude) vs. OS-level Seatbelt/Landlock/bubblewrap (Codex).
Headless / exec mode
Non-interactive run for scripting/CI: claude -p vs. codex exec.
Auto-memory
Claude Code's auto-generated persistent memory file; Codex has no documented equivalent.
Channels
Claude Code research-preview feature pushing external events (Telegram, Discord, …) into a live session via MCP.
Phase
This project's staged delivery unit. Phase 1 = docs; Phase 2 = interactive; Phase 3 = benchmarking.
